# OCS Plus 的 Fork 维护约定

本仓库以 Plus 默认分支保存稳定代码，以 `beta` 分支集成预览改动，以独立分支保留上游代码。同步上游、预览验收、合入稳定分支和发布版本分别确认；推送分支或通过 CI 不会自动创建 Release。本约定不增加运行时代码或定时同步任务。

同步遵循上游优先：平台适配、字体解密、导航、通用提取与匹配优先采用上游实现。Plus 仅保留 AI 提供商、联合决策、人工处理、单题重做、独立发布源等专属功能及必要的兼容桥接；桥接需要场景测试，不以整文件覆盖处理冲突。上游更新不改变 Plus 的独立版本序列，也不将已通过 Git 合并等同于运行验收完成。

## 仓库与分支

| 名称 | 用途 | 维护方式 |
| --- | --- | --- |
| `origin` | `broken-star1999/ocsjs-plus` | Plus 自己的仓库与发布源 |
| `upstream` | `ocsjs/ocsjs` | 只获取上游代码，不向这里推送 Plus 改动 |
| `feat/ai-answerer` | Plus 默认主分支 | 保存已经审核、合并的 Plus 功能与修复；正式版本从此分支确认的提交发布 |
| `beta` | 长期预览测试分支 | 接收开发与上游同步 PR；自动检查和体验验收通过后，再通过 PR 合入默认分支 |
| `5.0` | 上游镜像分支 | 纯粹跟踪 `upstream/5.0`，不加入 Plus 功能、版本号或专用修复 |
| `codex/*` | 临时功能、修复和测试分支 | 通常从最新 `beta` 创建，经验证和 PR 审核后合入 `beta`；合并后清理不再使用的分支 |
| `codex/sync-upstream-*` | 临时上游同步分支 | 从最新 `beta` 创建，再合并上游；解决冲突、验证兼容后通过 PR 合入 `beta` |

`5.0` 更新只表示本仓库取得了新的原版代码，不会直接更新已安装的 Plus 脚本。用户的安装与更新源仍是本仓库的 Plus Release。

日常流转为 `codex/*` → PR → `beta` → 验收 → PR → `feat/ai-answerer` → 正式发布。`beta` 只集成本次准备验收的改动；尚未准备好的功能继续留在各自开发分支。首次建立 `beta` 时，可以从已经本地验证的集成提交创建，后续改动统一走 PR。

默认分支上的紧急修复可从默认分支单独开发、审核和发布，之后及时通过 PR 合回 `beta`，避免预览分支漏掉正式版修复。包含上游同步的 PR 使用合并提交，保留原始提交关系，不使用 squash 或 rebase 合并。不要强制重置或覆盖长期分支，也不要通过反复删除、重建 `beta` 来清空测试进度。

## 同步前先检查 Actions

上游镜像应保留上游原貌，因此它可能包含上游自己的 GitHub Actions。旧的 **Release PR** 会响应 `5.0` 的推送，旧的 **Release Tag** 会响应合并到 `5.0` 的 PR；后者还可能继续触发构建发布。即使本次同步仅打算保存原版代码，也可能碰到这条继承的发布链。

Fork 仓库应在仓库级停用上述旧 **Release PR / Release Tag** 流程，并保留 **Verify OCS Plus** 验证。发布工作流只用于维护者明确选择、已经审核的 Plus 标签，不应由镜像分支的推送或上游发布间接触发。这里描述的是维护要求，是否已经停用须在 GitHub Actions 页面核对，不能仅凭本文认定。

每次同步还应检查上游新增或修改的工作流及其触发条件。仓库级停用现有流程不等于永久屏蔽将来新增的发布流程。不要为取消这些触发器而向纯镜像 `5.0` 混入 Plus 专用提交；需要保留的 Plus 工作流调整放在 Plus 分支审核。

GitHub 网页可以完成验证结果查看、PR 审核和手动发布；GitHub CLI 是可选工具，不是维护此 Fork 的前提。没有必要为了使用 CLI 另加一条自动发布链。

**Verify OCS Plus** 对 `feat/ai-answerer`、`beta` 和 `codex/*` 的推送运行检查，也检查目标为 `beta`、`feat/ai-answerer` 或 `5.0` 的 PR。检查成功后提供本次提交构建的 `ocs.user.js` 与 `ocs.meta.js` 工作流附件；这些附件可用于测试，不等同于已发布版本。

## 安全的日常步骤

以下命令用于说明操作顺序，不会由本文自动执行。切换分支前先确认工作区：有未提交改动时，先保存在所属功能分支或独立工作区，不要覆盖、丢弃不属于本次任务的文件。示例日期需替换，已有同名分支时也应改用新的名称。

### 1. 获取远端状态

```sh
git status --short
git remote -v
git fetch origin
git fetch upstream
```

核对 `origin` 和 `upstream` 的地址符合上表。`fetch` 只获取远端引用，不会把上游自动合入当前工作区。

### 2. 更新纯上游镜像

**先完成上一节的工作流检查，再推送镜像分支。** 对已经正确跟踪上游的镜像，只做快进更新：

```sh
git switch 5.0
git pull --ff-only origin 5.0
git merge --ff-only upstream/5.0
git push origin 5.0
```

更新后，本地 `5.0` 与 `upstream/5.0` 应指向同一提交，可用 `git rev-parse 5.0 upstream/5.0` 比较。如果不能快进或两个提交不一致，停止并检查是否有人向镜像加入了其他提交、上游是否改写了历史。不要用 `reset --hard`、强制推送或网页“丢弃提交”来自动解决，更不能对 Plus 默认分支执行这些覆盖操作。

### 3. 从预览分支集成上游

```sh
git switch beta
git pull --ff-only origin beta
git switch -c codex/sync-upstream-20261030
git merge --no-ff upstream/5.0
```

这样可以保留 Plus 的提交和上游的原始提交关系。发生冲突时逐项确认原版修复与 Plus 功能如何共存，特别注意题目提取、填写适配、更新源、构建元信息和工作流。不能把整份文件统一选成上游版本来省略兼容性检查。

如果本次合并需要放弃，可在确认仍处于该次合并过程后使用 `git merge --abort`，回到合并前的功能分支状态。不要通过重置 Plus 主分支来“回退同步”。

### 4. 验证后再提交 PR

从当前锁文件安装依赖，先构建工作区包，再运行集成测试；部分测试依赖构建后的包入口：

```sh
pnpm install --frozen-lockfile
npm run build
npm test
git diff --check
```

根据合并内容补充相关类型检查和浏览器场景。构建、离线模拟、真实 API、真实课程页面回填及保存／提交是不同的验证范围，PR 应写清本次实际完成了哪几项。

确认改动已经在同步分支提交后，将该分支推送到 `origin`，创建目标为 `beta` 的 PR。PR 说明至少包含上游提交范围、冲突处理、保留的 Plus 行为、验证结果与仍未实测的部分。**Verify OCS Plus** 通过后仍需维护者审核；CI 通过不等于自动接受合并或发布。

普通功能分支采用相同的 PR 路径。上游同步 PR 与新功能 PR 尽量分开，使兼容性变化容易检查，也便于定位回归。

### 5. 预览验收后合入稳定分支

`beta` 集成后先完成自动检查，再根据改动核验真实 API、课程页面及界面交互。需要分发测试版本时，从已确认的 `beta` 提交准备新版本号和标签，并按下一节的预发布流程操作。

一批预览改动验收通过后，创建 `beta` → `feat/ai-answerer` 的 PR，列明功能范围、测试结果和已知限制。审核通过后再合并；准备正式版本时移除预发布后缀并确认正式版本号。默认分支后续产生的版本或修复提交应再合回 `beta`，让下一轮开发包含最新稳定代码。

## Plus 发布与版本记录

正式版先把已经审核的改动合入 `feat/ai-answerer`，再确认用于发布的具体提交和 Plus 版本号。正式版发布标签必须指向默认分支中已经接受的提交，构建时检出该标签，而不是临时取某个仍在变化的分支最新代码。标签、`package.json`、脚本元信息和发布说明应一致。

Plus 使用自己的版本序列，例如 `0.1.5` 正式版与后续 `0.1.6-beta.1` 测试版；原版 OCS 基线另行记录，例如 `5.2.6`，并尽量附对应上游提交。同步上游不直接把原版版本号写成 Plus 版本号，也不因为上游发布就自动提升 Plus 版本。

测试版从 `beta` 中已确认的提交打新标签并标为预发布，独立记录测试标签和构建提交；正式版标为正式发布。现有手动发布工作流检出指定标签，核对标签与 `package.json` 版本一致，并将带预发布后缀的版本设置为预发布且不替换 Latest。测试版发布不会自动变成正式版；正式版需从审核后的默认分支提交重新确认版本与构建，不能只改已有测试 Release 的显示名称来代替这一步。

`beta` 分支本身不是测试更新通道。当前脚本仍使用本仓库正式 Latest 的更新地址；推送 `beta` 或发布下一版 Beta，不会使已安装脚本自动跟随预览分支。测试时可手动安装对应预发布附件；需要自动接收 Beta 更新时，另行实现并验证独立的测试更新通道。

发布属于单独的明确操作：审核更新说明、确认构建和测试、确认标签提交后，再由维护者手动运行发布流程或通过 GitHub 页面发布。本文不包含自动执行的创建标签、推送标签或创建 Release 命令。推送功能分支、更新 `5.0`、合并同步 PR 和运行 Verify 均不构成发布指令。

发布后核对 `ocs.user.js` 与 `ocs.meta.js` 附件、脚本版本与更新地址，并区分正式版和预发布状态。已发布标签和附件应保留可追溯性；需要修正发布内容时使用新的版本，避免无提示移动标签或替换用户已经安装的相同版本内容。

确需替换同一版本时，先备份原附件、SHA-256 和旧标签／提交记录，通过 PR 合入修复并验证；使用旧标签对象 SHA 校验后更新标签，在发布记录中保留旧新构建来源和附件摘要。附件上传后再次核对摘要与 Latest 状态，确保标签、发布记录和实际脚本对应同一份代码。同版本替换属于特殊维护操作，不作为常规自动更新流程。
